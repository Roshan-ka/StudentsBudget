# StudentsBudget P2.2 Implementation Plan: live sync

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development to implement this plan chunk by chunk. Steps use checkbox (`- [ ]`) syntax.

**Goal:** once a phone is linked to an account, every change syncs both ways by itself. Sync runs when the app opens, when it comes back online, every 60 s while it's open, and a few seconds after each change. Signed out, or without the Supabase settings, the app stays exactly as it is today.

**Status (2026-10-28): paused after day 1.** Day 1 (chunks 1–3) is built, reviewed and merged (PR #15 on SupportRW). On 2026-10-27 Roshan cut the rest down to push, pull and a **Sync now** button, in 1-hour chunks, with no automatic sync, backoff or week-recording gate. On 2026-10-28 the local MCP server ([[2026-10-28-mcp-server|MCP plan]]) went first: it reads, and doesn't need sync. P2.2 resumes when Claude should write to the account (adding an expense from a chat) or when two phones are in use.

**Builds on:** [[2026-10-23-p2-1-accounts-and-database|P2.1 plan]]: email-and-password accounts, eight owner-only tables in Supabase (Frankfurt), and the Save and Load buttons (PRs #13 and #14). **Spec:** [[Student Budget App - Concept]], P2 (:58, :71). Open items: [[Student Budget App - P1 follow-ups]].

## Why

With P2.1, two phones on one account drift apart until someone presses a button. A save from a phone that is behind also overwrites the other phone's changes. P2.2 replaces the buttons with automatic sync.

## How this plan is built

- **Eight chunks of about 2 hours, done one at a time.** Each ends with lint, typecheck, unit tests and its own e2e passing, then a commit. Roshan can stop or redirect between chunks.
- **Three days, one branch and one Draft PR each:**

| Day | Branch | Chunks | Visible to users? |
|---|---|---|---|
| 1 | `feat/p2-2-server-and-tracking` | 1–3 | No |
| 2 | `feat/p2-2-push-pull` | 4–6 | No: nothing is linked yet |
| 3 | `feat/p2-2-linking` | 7–8 | Yes: sync goes live |

- **End of each day:** full e2e on chrome and iphone, `test:offline`, and two parallel reviewers (data and UI).
- **Roshan, after each day's merge:** apply that day's migrations to the hosted project with `npx supabase db push`, or paste them into the SQL editor.

## Decisions

| Topic | Decision | Why |
|---|---|---|
| What changed | An outbox in Dexie records which rows changed. A Dexie middleware fills it and sees every write. | Every write path is covered, with no change to today's code. Nothing is recorded until the phone is linked. |
| What to send | The outbox holds only keys. A push reads each row as it is now: present → its data, gone → a deletion marker. | There are no stale copies to merge. |
| Deletes | Tombstones: the server row keeps its id, `data` becomes null, and `deleted_at` is set. | Another phone can only learn about a delete if the row is still there to read. |
| What's new on the server | A per-user revision counter in the database, bumped by a trigger on every write. A phone pulls everything after the last revision it has seen. | It doesn't rely on clocks and misses no row. Writes by one user wait on that user's counter row, so revisions become visible in order. |
| Conflicts | The last write to reach the server wins, per row. A row with a change still waiting on this phone isn't overwritten until that change is pushed. | Simple and predictable. The accepted loss: the plan is one row, so two phones editing it at the same moment keep only one edit. |
| Recurring entries | A server rule: a plan never moves a schedule's `postedThrough` back (chunk 8). | Otherwise an older plan could post an entry twice, or bring back a deleted one. Entry ids are already the same on every phone (`rec:<schedule>:<period>`). |
| Linking replaces Save and Load | On sign-in the phone links to the account. P2.1's save and load logic decides who wins the first time. After that there are no buttons, only a status line and "Sync now". | A save that overwrites another phone's changes can no longer happen. |
| Realtime | None. Sync runs on open, on `online`, every 60 s while visible, 3 s after a change, and on "Sync now". | Fewer moving parts, and iOS doesn't sync in the background anyway. |
| Sign-out, other accounts | Signing out keeps the data and the link, and sync pauses. The same account resumes; a different account is blocked until "Delete everything". | No data is ever mixed between accounts. |

## Chunks

### Chunk 1 – Server: revisions and deletion markers

- [ ] **New migration `…_sync.sql`.** For each of the 8 tables:
  - `data` becomes nullable;
  - add `deleted_at timestamptz` and `rev bigint not null default 0`;
  - replace the P2.1 check `<table>_data_check` with `(deleted_at is null) = (data is not null)`, plus the object and 64 kB check when `data` is set;
  - add an index on `(user_id, rev)`;
  - drop the "owner deletes" policy and revoke DELETE from `authenticated`. Deleting a user still cascades.
- [ ] **The counter:** a table `private.sync_meta (user_id primary key, rev)`, and a security-definer trigger `stamp_rev`. On every insert or update it writes the user's next revision into the row.
- [ ] **The pull:** `public.sync_pull(p_since bigint, p_limit int)` returns `(tbl, id, data, deleted_at, rev)` from all 8 tables after `p_since`, in revision order, at most `p_limit` rows.
  - It runs as the caller, so row-level security keeps it to the user's own rows.
  - It is granted to `authenticated` only.
- [ ] **P2.1 keeps working:**
  - `store.remove` writes tombstones;
  - `listIds` and `listRows` skip tombstones;
  - the e2e REST mock learns tombstones.
- [ ] **pgTAP `supabase/tests/sync.test.sql`:**
  - revisions rise with every write and are counted per user;
  - a tombstone has no data and a `deleted_at`;
  - a signed-in user can't hard-delete;
  - `sync_pull` gives only the caller's rows, in order, after the cursor, within the limit;
  - `anon` can't call it.
- **Done when:** `test:db` is green in CI, and the P2.1 save and load e2e still pass.

### Chunk 2 – Contract tests against a real Supabase stack

- [ ] **`src/sync/store.contract.test.ts`** runs only when `SUPABASE_TEST_URL` and `SUPABASE_TEST_KEY` are set. It:
  - signs up two random users on the local stack;
  - upserts, then reads 2,500 rows page by page;
  - writes tombstones;
  - pulls by revision with a limit;
  - checks that user B sees none of A's rows.
- [ ] **Script `test:contract`.** The CI `db` job runs it after `test:db`, with the settings from `npx supabase status -o env`. No secrets are needed.
- **Why:** the e2e mocks can drift from what PostgREST really does.
- **Done when:** the `db` job runs and passes it.

### Chunk 3 – Change tracking on the phone (hidden)

- [ ] **Dexie:** `db.version(4).stores({ outbox: '[table+key]', syncState: 'id' })`. `syncState` holds `{ id: 'current', userId, cursor, lastSyncedAt, problem }`.
- [ ] **`src/sync/track-changes.ts`:** a DBCore middleware (`db.use`).
  - It adds `outbox` to any read-write transaction that touches a synced table.
  - It records `{ table, key, seq }` on add, put and delete. Dexie's `update` and `modify` arrive as puts.
  - It skips `categories` and ECB rates, and ignores `deleteRange`: only `replaceAll` uses that, and chunk 7 handles it.
  - It records nothing unless tracking is on: an in-memory flag set at start from `syncState.userId`, and when a phone links.
  - Writes inside `untracked(fn)` are never recorded.
- [ ] **`src/sync/tables.ts`:** the Dexie-side registry, giving each table's key and its server id. For example, `fxRates` `[INR, manual]` becomes `INR`, the same rule as `serverRowsOf`.
- [ ] **Tests over every write path:**
  - `repo.ts`;
  - `rates.ts`, manual and ECB;
  - `post-due.ts` (`bulkAdd`);
  - `update-plan.ts`;
  - `suggested-budget.tsx` (`update`);
  - `set-default-account.ts` (`modify`);
  - `week-results.ts` (add, update, delete);
  - discount votes;
  - profile;
  - setup's `bulkAdd`.

  Tracking on records exactly the keys written. Tracking off records none, and `untracked` records none.
- **Done when:** these tests pass, and every existing unit and e2e test is unchanged.

### Chunk 4 – Push

- [ ] **`src/sync/push.ts`:**
  - it reads the outbox, then each key's row as it is now: present → upsert, gone → tombstone;
  - it writes in batches per table;
  - after each successful batch, it deletes the outbox entries whose `seq` is unchanged (compared with `===`, never `<=`: a `seq` only rises per row, not across tabs), so an edit made during the push stays queued.
- [ ] **`store.tombstone(table, ids)`**, which chunk 1's `remove` already uses.
- [ ] **Tests (fake store):**
  - a create, an edit and a delete each arrive;
  - an edit made during a push stays queued;
  - a failed push keeps the queue;
  - ECB rates are never sent;
  - a plan edit is sent as the whole plan row.

### Chunk 5 – Pull

- [ ] **`store.pull(since, limit)`** calls `sync_pull` through `client.rpc`.
- [ ] **`src/sync/pull.ts`:**
  - it pulls page by page after the cursor;
  - it checks each row with its row schema (`src/db/schemas.ts`). An invalid row stops the pull with "This app needs an update to sync", and the cursor stays put;
  - each page goes into one untracked Dexie transaction: rows are put, tombstones deleted, and keys waiting in the outbox skipped;
  - the new cursor is saved in the same transaction.
- [ ] **The fake store (`test-helpers.ts`)** gains revisions and tombstones, shared by two fake phones.
- [ ] **Tests:**
  - two fake phones converge after edits and deletes on both;
  - a change still waiting on a phone isn't overwritten;
  - an invalid row stops the pull;
  - the cursor only moves forward.

### Chunk 6 – Sync engine, triggers and status (still hidden: nothing is linked)

- [ ] **`src/sync/engine.ts` `syncNow()`:**
  - it runs one sync at a time;
  - it runs only when signed in, linked to this user and online;
  - it pushes, then pulls;
  - it records `lastSyncedAt` or the problem in `syncState`;
  - after an error it waits before retrying: 1, 2, 4 minutes and so on, up to 15.
- [ ] **`src/components/app-init.tsx`** gets a new start-up order:
  1. `ensureSeeded`;
  2. `syncNow` (8 s cap);
  3. refresh rates;
  4. post recurring;
  5. record weeks, only after a successful sync or on an unlinked phone, so two phones don't record the same week differently.
- [ ] **Triggers** (`src/components/sync-runner.tsx` in the layout): `online`, every 60 s while visible, and 3 s after the outbox changes (`liveQuery`).
- [ ] **Status** on the account page and the Settings card, with a **Sync now** button:
  - "Synced just now" or "Synced 2 min ago";
  - "3 changes waiting";
  - "Offline: changes wait on this phone";
  - "This app needs an update to sync".
- [ ] **Tests:**
  - engine unit tests: one sync at a time, offline, backoff, order;
  - the e2e REST mock learns revisions and `sync_pull`.

### Chunk 7 – Linking, which replaces Save and Load

- [ ] **On sign-in, and on open when signed in but not linked:**

  | This phone | The account | What happens |
  |---|---|---|
  | Linked to another account | anything | Blocked: "This phone holds another account's data. Sign out, or delete everything on this phone first." |
  | Empty | empty | Linked |
  | Has data | empty | Uploaded (P2.1 `planUpload` and `applyUpload`), then linked |
  | Empty | has data | Loaded (P2.1 `planDownload` and `replaceAll`), then linked |
  | Has data | has data | You choose, with counts and a backup offer: "Keep this phone's data" or "Use my account's data" |

  Linking sets `syncState` (user, cursor 0), turns tracking on, and runs `syncNow`.
- [ ] **Restore from a backup while linked:** needs nothing extra. Since the day-1 review, `replaceAll`'s `clear()` records the rows it removes and its adds record the new ones, so the next push makes the account match the restored phone. A test covers it.
- [ ] **A full comparison on linking and once a day:** a tab or installed app still on an older build writes without tracking. On link and once a day, compare every local row with the account's (P2.1's `planUpload` logic) and queue what differs.
- [ ] **Sign-out:** a push first when online. The data and the link stay, and sync pauses.
- [ ] **Delete everything:** also removes `syncState`, so the phone is unlinked. The account's copy stays.
- [ ] **Remove the "Save to my account" and "Load from my account" sections.** Their logic now lives in linking, and the account page shows the status and Sync now.
- [ ] **e2e with two phones:**
  - A links by uploading, B by loading;
  - an edit on A shows on B after Sync now;
  - a delete on B disappears on A;
  - the choice when both phones have data;
  - a different account is blocked;
  - signing out pauses sync and keeps the data.

### Chunk 8 – Plan watermarks, docs, end of the plan

Name it to sort before `stamp_sync` (e.g. `keep_watermarks`): BEFORE triggers fire in name order, and `deleted_at` must be decided on the final data.
- [ ] **README:** Account describes sync instead of Save and Load, and Privacy says when data is sent.

## Not in this plan

- Realtime (instant updates from the other phone) and background sync on iOS.
- Purging old tombstones; the data is small enough for now.
- Merging two edits to the same row; the last write wins.
- From P2.3: account deletion in the app, password reset, the privacy notice and Impressum before friends join, and invite-only sign-up.
